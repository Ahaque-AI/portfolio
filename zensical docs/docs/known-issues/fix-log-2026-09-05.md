# Introduction form required too much scrolling

## Symptom and cause

The owner reported that inputs/actions were below the initial viewport.
The form displayed every field, a large comment box, and both completion
messages beneath a tall introduction. Mobile devoted 325px to the hero alone.

## Resolution

Kept the approved visual identity and orbit behavior. Split entry into name
and contact steps, with comments collapsed initially, retained the name-only
path, added Back with preserved values, and replaced the form on completion.
Short viewports allocate less height to decorative regions. Scrolling remains
available when expanded content, a keyboard, or zoom needs it.

## Verification

`pnpm check`, `pnpm test` (five tests), and `pnpm build` passed. Validation tests
cover full and name-only requirements; the copy check guards against prohibited dashes.
Browser testing belongs to the owner. Manual checks: name-only on both steps,
Enter to advance, Back preserving values, expanding a note, agreement errors,
completion recovery, narrow screens, reduced motion, and keyboard visibility.

## Three.js orbital navigation

- Symptom: the route-ahead link needed a continuous orbital transition and the
  onboarding diagram needed more visual depth.
- Resolution: owner-requested Three.js globe expansion and shader dissolve;
  Astro ClientRouter persists the live canvas across the page swap. The actual
  destination is ready before covering the screen. The map shares the 3D globe
  and preserves its SVG fallback. Page scripts reinitialize after navigation;
  animation loops, geometry, materials and render targets are cleaned up.
- Resilience: reduced motion and history traversal skip the flight. Escape
  skips motion, failed GPU setup uses ordinary navigation, and an aborted older
  load cannot dispose a newer flight. No form data is persisted or sent.
- Verification: pnpm check, pnpm test (11 tests), pnpm build (four routes), and
  strict premium audit. Vite reports the dynamically loaded Three.js chunk over
  500 kB. The Impeccable detector reports design-token advisories. Browser shader
  compilation, visual timing, narrow-layout and keyboard checks remain manual
  owner checks; no browser controls were used.

## Onboarding route-map labels and movement

- Symptom: the route labels in the map competed with orbital geometry. Arrival
  was visually cramped at the lower edge, while future destinations felt like
  loose captions.
- Resolution: replaced them with aligned, indexed route annotations. Arrival
  remains a semantic link and gains a stable hover and focus frame. Added a
  deterministic Three.js star field, orbital shimmer, signal halo and bounded
  mouse-only camera parallax. The scene remains static under reduced motion.
- Verification: Astro type check passed. Unit coverage now asserts that Three.js
  point geometry is released with meshes and lines. Manual visual verification
  remains with the owner.

## Returning visitor name preference

- Symptom: the Arrival marker itself was not the control, and returning visitors
  repeated the name step despite having already completed it.
- Resolution: Arrival is now the native SVG link with a 60px hit circle,
  hover, focus and pressed feedback. A successfully validated name is saved
  under one local-storage key, then an existing name redirects `/` to the route
  map. Storage failures retain the normal flow. Privacy and terms describe the
  local-only purpose, recipients and browser-data deletion path.
- Verification: `pnpm check`, `pnpm test` with 13 passing tests, and `pnpm build`
  passed. Browser verification remains with the owner.

## Returning visitor edit loop

- Symptom: Back to introduction and the Arrival control sent a returning visitor
  to `/`, where the saved-name redirect immediately returned them to the map.
- Resolution: those controls now explicitly open the introduction in edit mode.
  Edit mode clears the one saved local name before the form loads, so a new
  valid submission replaces it and normal return visits still skip the form.
- Verification: covered by visitor-name storage tests; browser link behaviour
  remains an owner check.

## Orbit transition continuity

- Symptom: the transition globe expanded and faded out, which lost the spatial
  relationship with the incoming page’s orbit.
- Resolution: the Three.js scene measures the incoming orbit after the Astro
  swap and contracts into that visible position, then hands off directly with no page-wide fade.
- Verification: focused source contract coverage added; visual timing remains
  an owner check.

## Flight asset isolation

- Symptom: hiding source page orbit artwork during flight also removed visitor
  markers and annotations, making them appear coupled to navigation.
- Resolution: flight-only Three.js geometry is now separate from page SVGs.
  SVGs provide only the measured orbit positions; their labels stay page-local.

## Flight landing alignment

- Resolution: the destination map pauses its idle rotation during the handoff,
  while the flight uses a higher-order easing curve and a longer landing. The
  orbit comes to rest at the same visual state it hands off to.

## Seamless flight handoff

- Symptom: the owner reported that landing still was not seamless. The
  destination assets changed at the handoff and their position shifted a
  little, and the swap was an abrupt cut rather than a fade.
- Cause: the map animated on absolute `performance.now()` while the landing
  froze its clock at zero, so resuming jumped the globe spin, the signal
  position and the route opacity to a mid-animation state. The map's ring
  group also started idle motion at a 0.04 radian yaw while the flight settled
  at exactly zero, and the overlay canvas was removed instantly.
- Resolution: the map now runs its own delta clock that simply stops
  advancing while the flight lands, so motion resumes from the exact landing
  frame (`src/scripts/orbital-map.ts`). Its idle yaw phase starts at zero to
  match the settled flight pose. After landing, the overlay crossfades out
  over 450ms while the identical live scene sits beneath it, then disposes
  (`src/scripts/orbital-three.ts`, `.is-fading` rule in `src/styles/global.css`).
  The home intro globe now scales with the SVG's actual letterboxed fit, so
  the flight also starts exactly on the visible globe on clamped layouts
  (`src/scripts/orbital-intro.ts`).
- Verification: `pnpm check` (0 errors), `pnpm test` (16 passing), `pnpm build`
  (four routes) passed. Visual timing and the crossfade feel remain manual
  owner checks; no browser controls were used.
- Regression fix, same day: the first crossfade left `.is-fading` on the
  persistent `#orbit-flight` host, so every later flight started at opacity
  zero and navigation looked stuck or dead. `dispose()` and `createFlight()`
  now clear the class, and the opacity transition only applies while fading
  out, so a new flight starts fully visible with no fade-in. Re-verified with
  `pnpm check`, `pnpm test` (16 passing) and `pnpm build`.
